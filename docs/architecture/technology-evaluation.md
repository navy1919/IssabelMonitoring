## ۲. روش ارزیابی

### ۲.۱ معیارها (برگرفته از منشور محصول §5)

برای دسته‌های زیرساخت داده از فهرست مشترک زیر استفاده می‌شود. برای زبان، Collector و Frontend معیارهای تخصصی همان دسته تعریف شده که هر کدام به یکی از این معیارهای پایه نگاشت می‌شود.

| کد | معیار | تفسیر امتیاز ۵ |
|---|---|---|
| C01 | Throughput / کارایی نوشتن | پشتیبانی راحت از سناریوی High با حاشیه |
| C02 | تطابق با الگوهای Query | الگوهای اصلی ما (سری زمانی + رویداد + خلاصه تراکنش، group-by با cardinality بالا، join با ابعاد) به‌صورت بومی |
| C03 | رشد ذخیره‌سازی / فشرده‌سازی | فشرده‌سازی ستونی قوی، ردپای کم دیسک |
| C04 | Retention و حذف | TTL به ازای کلاس داده، حذف ارزان (drop partition) |
| C05 | مقیاس‌پذیری | مقیاس افقی بدون بازطراحی |
| C06 | HA/DR | Replication بومی، failover مستند، استقلال failure domain |
| C07 | پیچیدگی عملیاتی (امتیاز بالاتر = ساده‌تر) | تعداد اجزای کم، ابزار مدیریت شناخته‌شده |

### ۲.۳ محاسبه

امتیاز وزنی = Σ (وزن × امتیاز) / 100 ، بازه ۱ تا ۵. وزن‌های هر جدول جمعاً ۱۰۰ است. تفاوت کمتر از **۰٫۲۵** «تساوی عملی» تلقی می‌شود و تصمیم با معیارهای کیفی (ریسک، ADR مرتبط) گرفته می‌شود.

### ۲.۴ فرض‌های صریح ارزیابی

- [فرض A-01] بانک واحد، تک‌مستأجر؛ PROD/DR/UAT و دو سایت.
- [فرض A-02] ماشین‌های مجازی Linux سازگار با RHEL؛ Kubernetes برای خود پلتفرم فرض نشده.
- [فرض A-03] تیم ۴ تا ۸ مهندس — بنابراین وزن «پیچیدگی عملیاتی» و «تعداد فناوری‌های متمایز» بالا است.
- [فرض A-11] سناریوهای Low/Medium/High (نگاه کنید به [capacity-planning.md](capacity-planning.md)) واقعیت را در بر می‌گیرند. امتیازهای Throughput نسبت به سناریوی **Medium** داده شده و High در تحلیل حساسیت بررسی می‌شود.
- [فرض A-12] بدون اینترنت؛ mirror داخلی artifact موجود است یا ساخته می‌شود.
- [فرض] مهارت تیم در Java در بانک‌های ایرانی رایج است (تأییدنشده؛ [باز Q-01]).
- [فرض] تهیه مجوز تجاری و پشتیبانی رسمی از برخی فروشندگان خارجی به دلیل محدودیت‌های تحریمی و ارزی دشوار یا ناممکن است؛ این فرض امتیاز C08 محصولات تجاری را کاهش می‌دهد. **نیازمند بررسی حقوقی/تأیید (Q-21).**
- [توصیه] اصل «کمترین تعداد فناوری ذخیره‌سازی متمایز»: هر Store اضافی هزینه عملیاتی، Backup، ارتقا و امنیت جداگانه دارد.

توضیح امتیازهای کلیدی:
- **L1 – Java = 5:** کلاینت رسمی IBM MQ برای Java (JMS و PCF) و JMX بومی JVM است؛ بیشترین پوشش برای اتصال‌دهنده‌های middleware بانکی. (نیازمند تأیید نسخه کلاینت سازگار با نسخه MQ بانک — Q-08)
- **L1 – Go = 2:** کتابخانه MQ برای Go (پوشاننده کلاینت C) وجود دارد ولی JMX ندارد؛ اتصال به JMX نیازمند واسطه (مثلاً Jolokia) است که تغییر پیکربندی سمت برنامه‌ها می‌طلبد (مغایر NFR-IMP-002). نیازمند تأیید.
- **L1 – .NET = 4:** کلاینت IBM MQ برای .NET (XMS/.NET classes) وجود دارد؛ JMX ندارد. نیازمند تأیید.
- **L2:** فقط فرض است. اگر تیم واقعی عمدتاً .NET باشد، نتیجه می‌تواند عوض شود (§۳.۴).
- **L6 – .NET 8 = 4:** طبق دانش عمومی، پشتیبانی .NET 8 LTS در نوامبر 2026 پایان می‌یابد؛ انتخاب واقعی در صورت .NET، نسخه LTS بعدی (.NET 10) خواهد بود. نیازمند تأیید.

### ۳.۳ نتیجه
[توصیه] **Java 21 LTS + Spring Boot 3.x** برای `platform-core` و `connector-runtime` (منطبق با ADR-0003). Kotlin از نظر فنی هم‌تراز است ولی مهارت تیم (L2) آن را عقب می‌اندازد؛ می‌توان در آینده Kotlin را در همان JVM برای ماژول‌های خاص پذیرفت. Python فقط برای آزمایش‌های تحلیلی جداشده در فاز ۵، در صورت توجیه. Go برای خود ما کد نوشته نمی‌شود؛ OTel Collector (Go) به‌صورت باینری پیش‌ساخته مصرف می‌شود (ADR-0004).

وضعیت: **Blocked on Q-01** — تا معلوم شدن مهارت واقعی تیم، تصمیم نهایی نیست.

یادداشت‌ها (همه نیازمند تأیید در نسخه انتخابی):
- OTel Collector: persistent queue با extension `file_storage`؛ redaction با processorهای `transform`/`redaction`/`attributes`؛ ساخت توزیع حداقلی با OpenTelemetry Collector Builder (OCB) که سطح حمله و اندازه باینری را کم می‌کند. K6 = 3 به‌خاطر پیکربندی YAML پیچیده و تغییرات مکرر نسخه‌های contrib.
- Telegraf: plugin فراوان (از جمله SNMP)؛ بافر عمدتاً حافظه‌ای (پشتیبانی بافر دیسکی در نسخه‌های جدید — تأیید شود).
- Vector: بافر دیسکی و end-to-end acknowledgement قوی، VRL برای redaction قوی؛ اما OTLP و پوشش متریک کمتر بالغ و مالکیت تجاری.
- هیچ‌کدام برای APIهای Zabbix/SolarWinds/Splunk/MQ PCF پشتیبانی بالغ و قابل‌اتکا ندارند (K2)؛ این دلیل اصلی وجود `connector-runtime` به زبان Java است.

### ۴.۳ نتیجه
[توصیه] معماری **ترکیبی** (ADR-0004): `edge-collector` = توزیع سفارشی OTel Collector برای پروتکل‌های استاندارد و push؛ `connector-runtime` = Java برای APIهای فروشنده با الگوی pull. هر دو به ازای هر Zone، فقط با اتصال خروجی. امتیاز ترکیبی عملاً بیشینه K1 و K2 را می‌گیرد.

NATS JetStream در W-now عملاً هم‌تراز است، ولی افزودن آن یک فناوری جدید بدون نیاز فعلی است. وقتی triggerها فعال شوند (پایدار بیش از حدود ۵۰ هزار رکورد در ثانیه، نیاز به replay چندمصرف‌کننده، fan-in چندسایتی، یا تحمل قطع نقش ingest بیش از بافر ≥ ۴ ساعت collector)، **Kafka (KRaft)** با W-scale برنده است (اکوسیستم، Kafka engine در ClickHouse، مجوز Apache 2.0). Redpanda به دلیل BSL رتبه دوم است (Q-21).

**تحلیل حساسیت:** اگر بانک از قبل خوشه Kafka تحت بهره‌برداری با تیم مسئول داشته باشد ([باز Q-09]؛ Kafka S4=4، S6=4 چون هزینه عملیات مشترک است): W-now → Kafka = 4.55 > بدون Bus = 4.10. «نکته برای بازبینی»: پاسخ Q-09 می‌تواند ADR-0010 را حتی پیش از trigger‌ها تغییر دهد؛ البته استفاده از Kafka مشترک بانک یعنی اشتراک failure domain (NFR-AVL-002) که باید سنجیده شود.
